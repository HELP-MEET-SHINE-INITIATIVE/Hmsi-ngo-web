# HMSI Retention Audit Logging Specification

**Purpose:** Define the audit logging model required to demonstrate, investigate, and report on every material retention state transition, suppression decision, exception, approval, retry, failure, and access review in the HMSI CRM and Typeform/CRM retention pipeline.

**Status:** Implementation-ready, CRM-agnostic specification  
**Related documents:**

- [HMSI Data Governance and Volunteer Privacy Compliance Policy](./hmsi-data-governance-volunteer-privacy-compliance-policy.md)
- [HMSI CRM Retention and Suppression Configuration Runbook](./hmsi-crm-retention-suppression-configuration-runbook.md)
- [HMSI Staged Retention Automation Scripts and Workflow Rules](./hmsi-staged-retention-automation-scripts.md)
- [HMSI Staged Retention State Machine Acceptance Test Checklist](./hmsi-staged-retention-acceptance-test-checklist.md)

> **Important:** This is a technical governance specification, not formal legal advice. HMSI should confirm the final audit-retention period, controller/processor obligations, regulatory reporting requirements, legal-hold rules, and evidence standards with its qualified privacy adviser.

## 1. Objectives and audit boundary

The audit system must answer five questions for every material action:

1. **What happened?** The event type, result, state transition, suppression decision, or exception.
2. **Which controlled object was affected?** A non-reversible reference or short cryptographic hash, not unnecessary personal data.
3. **Why did it happen?** The rule version, reason code, approval reference, hold, request, incident, or operator purpose.
4. **Who or what caused it?** A named human actor, service account, workflow, or scheduler, with authorization context.
5. **What evidence proves the result?** Batch/run ID, timestamp, provider result, checksum, bounded counts, and linked follow-up event.

The audit ledger is an accountability record, not a second CRM. It must not contain volunteer names, email addresses, phone numbers, HMSI IDs, raw feedback, safeguarding narratives, passwords, access tokens, webhook secrets, unrestricted CRM URLs, or full source payloads. Use a scoped internal reference or keyed hash when correlation is necessary.

The audit boundary includes:

| Area | Events that must be logged |
|---|---|
| State machine | Every accepted, rejected, skipped, or failed state transition |
| Retention review | Candidate selection, eligibility result, owner assignment, and approval decision |
| Holds | Hold creation, change, review, release, expiry escalation, and disposal skip |
| Suppression | Applied, renewed, removed, rejected, expired, and exception decisions |
| Rights and incidents | Request/incident gate creation, disposal block, review, and release |
| Anonymisation/deletion | Planned, approved, attempted, completed, failed, unknown-result, reconciled, and downstream outcomes |
| Imports/exports | Source receipt, checksum, schema result, reconciliation, quarantine, and export eligibility |
| Access | Privileged access grants, removals, reads of restricted views, exports, and access reviews |
| Operations | Job start/end, lock conflict, retry, alert, pause, configuration change, and recovery |

## 2. Audit event identity and integrity

Every event must have a unique `event_id` generated by the audit service. A state transition also has a stable `transition_id`; retries reference the same transition rather than creating an apparently unrelated action. A scheduled run has a `run_id`, and a batch within a run has a `batch_id`.

Use UTC timestamps and distinguish event creation time from source event time and provider completion time. A cryptographic hash of the controlled object reference should be generated with a server-side keyed HMAC or equivalent so that an exposed audit export cannot be used as a simple lookup table. Store the key outside the audit store and rotate it under a documented process.

The ledger should be append-only or tamper-evident. At minimum, each event should include a hash of its canonical representation and a reference to the previous event or batch digest. If the selected platform provides immutable/WORM retention or an append-only audit service, use it for the authoritative copy.

```ts
export type AuditResult =
  | "planned"
  | "accepted"
  | "completed"
  | "skipped"
  | "rejected"
  | "failed"
  | "unknown";

export type ActorType = "human" | "service" | "workflow" | "scheduler";

export interface RetentionAuditEvent {
  eventId: string;
  eventType: string;
  schemaVersion: string;
  occurredAtUtc: string;
  recordedAtUtc: string;
  environment: "test" | "staging" | "production";
  runId?: string;
  batchId?: string;
  transitionId?: string;
  objectClass?: string;
  objectRefHash?: string;
  sourceRefHash?: string;
  previousState?: string;
  nextState?: string;
  result: AuditResult;
  reasonCode?: string;
  ruleVersion?: string;
  mappingVersion?: string;
  suppressionRuleVersion?: string;
  actorType: ActorType;
  actorRefHash?: string;
  authorizationRole?: string;
  purposeCode?: string;
  approvalRefHash?: string;
  holdRefHash?: string;
  rightsRequestRefHash?: string;
  incidentRefHash?: string;
  provider?: string;
  providerOperation?: string;
  providerRequestRefHash?: string;
  retryAttempt?: number;
  errorClass?: string;
  countBand?: "0" | "1-4" | "5-9" | "10-24" | "25+";
  qualityState?: string;
  suppressionState?: "visible" | "suppressed" | "insufficient_data";
  payloadDigest?: string;
  previousEventDigest?: string;
  eventDigest: string;
}
```

## 3. Event taxonomy

Use stable snake-case event names. New event types require a schema version and data-minimisation review. Do not create free-form event names at runtime.

### 3.1 Run and batch events

| Event type | Required fields | Result meaning |
|---|---|---|
| `retention_run_started` | `runId`, actor, environment, rule version | Scheduler accepted a run |
| `retention_run_lock_conflict` | `runId`, reason, actor | Another run is active; no processing occurred |
| `retention_batch_started` | `runId`, `batchId`, count band | Candidate batch was read |
| `retention_batch_completed` | `batchId`, count band, result | Batch completed with bounded outcome |
| `retention_run_completed` | `runId`, counts, result | Run completed, held, or failed |
| `retention_run_paused` | `runId`, reason, actor | Run was intentionally stopped |
| `retention_configuration_changed` | actor, changed setting class, approval ref | Retention mode, batch, rule, or allowlist changed |

Exact record counts may be restricted where they create inference risk. Use count bands in general reports while preserving exact counts only in a tightly restricted operations store if genuinely required.

### 3.2 State-transition events

| Event type | Required fields | Examples |
|---|---|---|
| `retention_state_transition_planned` | object class/ref hash, previous/next state, rule version | `active → review_due` |
| `retention_state_transition_accepted` | transition ID, previous/next state, actor, reason | CRM accepted transition |
| `retention_state_transition_rejected` | transition ID, current state, attempted state, reason | Illegal transition or missing gate |
| `retention_state_transition_failed` | transition ID, error class, result | Provider or validation failure |
| `retention_state_transition_reconciled` | transition ID, final state, reconciliation result | Recovery verified final state |

The transition must be written only after the state change is confirmed, except for a `planned` event. A `completed` transition without an associated provider or CRM result is invalid.

### 3.3 Review and eligibility events

| Event type | Required fields | Purpose |
|---|---|---|
| `retention_candidate_selected` | run/batch, record class, count band | Shows how the candidate entered review |
| `retention_review_ready` | object class/ref hash, review rule, result | All non-destructive review gates passed |
| `retention_review_blocked` | reason code, object class, owner role | A gate prevented progression |
| `retention_review_assigned` | owner role/ref hash, purpose code | Review responsibility was assigned |
| `retention_approval_requested` | batch ID, object class, approval type | Named approval required |
| `retention_approved` | reviewer actor, approval ref hash, next state | Approved for anonymisation or deletion |
| `retention_approval_rejected` | reviewer, reason code | Approval denied or returned |

The audit record should identify the accountable role and approval reference without placing the substantive case narrative in the ledger.

## 4. Suppression audit model

Suppression is a privacy and quality control. It is not a performance rating, disciplinary flag, or volunteer status. The audit model must distinguish the initial suppression decision, later review, and any attempted override.

### 4.1 Suppression events

| Event type | When to emit it | Required fields |
|---|---|---|
| `suppression_applied` | A source record is excluded from aggregate use | object hash, reason, rule version, result |
| `suppression_reaffirmed` | A scheduled review confirms suppression remains necessary | prior reason, reviewer/system, next review date if applicable |
| `suppression_removed` | A named privacy reviewer releases suppression | reviewer, approval ref, reason, rule version |
| `suppression_removal_rejected` | Release attempt fails a privacy gate | actor role, reason code, current suppression state |
| `suppression_exception_created` | Rule cannot safely decide | exception reason, owner role, due date |
| `suppression_exception_resolved` | Exception receives a controlled decision | decision, reviewer, next state |
| `suppression_export_blocked` | Export attempted to include suppressed data | export ID, view, rule version, result |
| `suppression_cross_filter_blocked` | A filter would create a re-identification risk | dashboard view, rule version, bounded cohort state |
| `suppression_rule_changed` | Rule or threshold changes | version, approval ref, effective time |

### 4.2 Required suppression reasons

Use a controlled reason code. Do not permit free-form operational explanations in the audit event.

```text
small_cell
cross_filter_risk
confidential_route
unresolved_identity
sensitive_content
quality_failure
unknown_mapping
rights_request
open_incident
manual_privacy_review
restricted_record_class
```

A `small_cell` or `cross_filter_risk` event should record the rule version and bounded cohort state, not the exact list of people in the cell. A `confidential_route` or `sensitive_content` event should not expose the underlying narrative.

### 4.3 Suppression exception workflow

1. The source or aggregate layer detects a suppression condition.
2. The system applies suppression and emits `suppression_applied`.
3. If the condition is ambiguous, the system creates `suppression_exception_created` and assigns the privacy queue.
4. The reviewer selects only an approved outcome: retain suppression, adjust a coded field, route confidentially, or release after evidence review.
5. The system emits `suppression_exception_resolved` and, where relevant, `suppression_removed`.
6. The next export or dashboard read re-applies suppression server-side.

No ordinary administrator may remove suppression by directly editing a Boolean field. The approved workflow must validate the reviewer role, reason, rule version, and authorization scope.

## 5. Hold, rights, incident, and correction events

A disposal action is blocked when a valid hold, open rights request, open incident, or pending correction exists. Each block must be explainable without revealing the sensitive matter.

| Event type | Required fields |
|---|---|
| `hold_created` | hold ref hash, record class/ref hash, owner role, reason code, review date |
| `hold_updated` | hold ref hash, changed field classes, actor, reason code |
| `hold_review_overdue` | hold ref hash, owner role, due date, escalation level |
| `hold_disposal_skipped` | batch/run, record class/ref hash, reason code |
| `hold_released` | reviewer, approval ref, release reason, timestamp |
| `rights_request_gate_created` | request ref hash, request type, record class, owner role |
| `rights_request_disposal_blocked` | request ref hash, object class/ref hash, result |
| `rights_request_gate_released` | reviewer, outcome, timestamp |
| `incident_disposal_blocked` | incident ref hash, object class, reason code |
| `correction_disposal_blocked` | correction ref hash, object class, reason code |
| `restricted_schedule_excluded` | record class, rule version, result |

Do not put the contents of a safeguarding report, legal advice, incident narrative, or rights correspondence into the audit event. Store only a protected reference hash and controlled status.

## 6. Anonymisation and deletion events

Anonymisation and deletion require separate event chains. The audit trail must make it possible to show that a record was approved, checked immediately before execution, acted upon, and reconciled afterward.

### 6.1 Anonymisation event chain

```text
anonymisation_planned
  → anonymisation_approved
  → anonymisation_preflight_passed
  → anonymisation_started
  → anonymisation_completed
  → anonymisation_reconciled
```

If any stage fails, emit `anonymisation_failed` or `anonymisation_blocked` and do not proceed to the next stage. Record the number or classes of removed fields, not the removed values.

### 6.2 Deletion event chain

```text
delete_candidate_selected
  → deletion_approved
  → deletion_preflight_passed
  → deletion_started
  → deletion_provider_accepted
  → deletion_reconciled
  → deletion_completed
```

A provider timeout after `deletion_provider_accepted` must result in `deletion_unknown_result`, not `deletion_completed`. The recovery process must reconcile the CRM and downstream stores before any retry.

| Event type | Required fields |
|---|---|
| `deletion_preflight_blocked` | reason code, gate, object class/ref hash |
| `deletion_started` | transition ID, approval ref hash, batch ID |
| `deletion_provider_accepted` | provider, operation, bounded provider request hash |
| `deletion_unknown_result` | provider, error class, retry blocked flag |
| `deletion_reconciled` | provider state, result, reconciliation run ID |
| `deletion_completed` | final result, downstream disposition, disposal reference |
| `deletion_failed` | error class, retry eligibility, owner role |

## 7. Database model

A relational implementation should separate append-only events from derived reporting views. The following is illustrative and must be adapted to the actual database and migration process.

```sql
CREATE TABLE retention_audit_events (
  event_id UUID PRIMARY KEY,
  event_type TEXT NOT NULL,
  schema_version TEXT NOT NULL,
  occurred_at_utc TIMESTAMPTZ NOT NULL,
  recorded_at_utc TIMESTAMPTZ NOT NULL DEFAULT now(),
  environment TEXT NOT NULL CHECK (environment IN ('test', 'staging', 'production')),
  run_id TEXT,
  batch_id TEXT,
  transition_id TEXT,
  object_class TEXT,
  object_ref_hash TEXT,
  source_ref_hash TEXT,
  previous_state TEXT,
  next_state TEXT,
  result TEXT NOT NULL CHECK (result IN ('planned','accepted','completed','skipped','rejected','failed','unknown')),
  reason_code TEXT,
  rule_version TEXT,
  mapping_version TEXT,
  suppression_rule_version TEXT,
  actor_type TEXT NOT NULL CHECK (actor_type IN ('human','service','workflow','scheduler')),
  actor_ref_hash TEXT,
  authorization_role TEXT,
  purpose_code TEXT,
  approval_ref_hash TEXT,
  hold_ref_hash TEXT,
  rights_request_ref_hash TEXT,
  incident_ref_hash TEXT,
  provider TEXT,
  provider_operation TEXT,
  provider_request_ref_hash TEXT,
  retry_attempt INTEGER CHECK (retry_attempt IS NULL OR retry_attempt >= 0),
  error_class TEXT,
  count_band TEXT,
  quality_state TEXT,
  suppression_state TEXT,
  payload_digest TEXT,
  previous_event_digest TEXT,
  event_digest TEXT NOT NULL,
  UNIQUE (event_id),
  UNIQUE (transition_id, event_type, retry_attempt)
);

CREATE INDEX retention_audit_events_run_idx
  ON retention_audit_events (run_id, occurred_at_utc);

CREATE INDEX retention_audit_events_object_idx
  ON retention_audit_events (object_ref_hash, occurred_at_utc);

CREATE INDEX retention_audit_events_suppression_idx
  ON retention_audit_events (event_type, suppression_rule_version, occurred_at_utc);
```

The audit writer must reject events that contain disallowed fields. Use database roles or row-level policies so application users can insert only through a controlled function and cannot update or delete existing audit events. A service or privacy role may read restricted fields; ordinary dashboard roles should receive only derived compliance summaries.

## 8. Derived compliance reporting views

Do not provide the raw audit table to ordinary administrators. Create purpose-specific views that expose bounded evidence.

### 8.1 State-transition compliance view

```sql
SELECT
  date_trunc('day', occurred_at_utc) AS event_day,
  object_class,
  previous_state,
  next_state,
  result,
  count(*) AS transition_count,
  count(*) FILTER (WHERE approval_ref_hash IS NOT NULL) AS approved_count,
  count(*) FILTER (WHERE error_class IS NOT NULL) AS error_count
FROM retention_audit_events
WHERE event_type IN (
  'retention_state_transition_accepted',
  'retention_state_transition_rejected',
  'retention_state_transition_failed',
  'retention_state_transition_reconciled'
)
GROUP BY 1, 2, 3, 4, 5;
```

### 8.2 Suppression-exception report

```sql
SELECT
  date_trunc('month', occurred_at_utc) AS reporting_month,
  reason_code,
  suppression_rule_version,
  result,
  count(*) AS exception_count,
  count(*) FILTER (WHERE authorization_role IN ('privacy_lead', 'dpo')) AS privacy_reviewed_count
FROM retention_audit_events
WHERE event_type IN (
  'suppression_applied',
  'suppression_exception_created',
  'suppression_exception_resolved',
  'suppression_removal_rejected',
  'suppression_cross_filter_blocked'
)
GROUP BY 1, 2, 3, 4;
```

### 8.3 Destructive-operation control report

The compliance report should show counts and control outcomes, not individual records.

| Metric | Calculation | Control question |
|---|---|---|
| Review candidates | Candidate events by period and record class | Did the scheduled review run? |
| Hold blocks | `hold_disposal_skipped` count | Were holds respected? |
| Rights blocks | Rights-gate block count | Were open rights requests protected? |
| Suppression applications | Suppression events by reason | Which privacy controls operated? |
| Approval coverage | Destructive completions with approval reference ÷ destructive completions | Was approval present? |
| Audit completeness | Completed transitions with matching terminal event | Can outcomes be evidenced? |
| Unknown deletion results | `deletion_unknown_result` count | Are unresolved provider outcomes open? |
| Retry exhaustion | Failed events at retry limit | Which operational failures need remediation? |
| Restricted exclusions | Restricted schedule exclusion count | Did sensitive records stay outside ordinary automation? |
| Access exceptions | Denied privileged actions or export blocks | Were boundaries enforced? |

Rates should be suppressed or marked unavailable when the denominator is missing or itself privacy-sensitive.

## 9. Access control and audit-of-audit controls

The audit system must protect the records that prove compliance. Use separate roles:

| Role | Permission |
|---|---|
| Audit writer service | Append events; no update/delete; no unrestricted read |
| Pipeline operator | Read run summaries and bounded failures; no raw restricted references |
| Privacy lead/DPO | Read restricted audit evidence and manage suppression/hold reviews |
| Security reviewer | Read access, configuration, and integrity events |
| CRM administrator | Read configuration and operational outcomes; no unrestricted sensitive narrative |
| Programme director | Read aggregate compliance summaries only |
| Ordinary team lead | No audit-ledger access; receives only approved operational status |

Every read of restricted audit data must itself be logged as `audit_accessed`, including actor role, purpose code, view name, time, and bounded result. Logging a read must not create a recursive audit loop; access events can be written to a dedicated security audit stream that is periodically reconciled with the retention ledger.

The audit writer must reject client-supplied actor identity, role, purpose, approval reference, or state transition. These values must be derived from authenticated server context or a trusted scheduler/workflow identity.

## 10. Retention and disposal of audit events

Audit retention is a policy decision, not a default database setting. The proposed HMSI default is 24 months minimum for bounded audit metadata, subject to legal, grant, safeguarding, security, and records-management review. Raw source payloads and narratives must not be copied into the audit ledger simply to extend their retention.

When audit records reach their approved end date, run a separate audit-retention review. A legal hold, open incident, unresolved rights request, or active investigation may suspend disposal of relevant audit evidence. The hold must be documented using a reference hash, owner, review date, and reason code.

Audit disposal itself generates a summary event in a separate protected system or archive, containing the disposal batch ID, event class, count band, rule version, approver, and completion result. Do not delete the final evidence of the disposal action before the retention policy permits it.

## 11. Monitoring and alert thresholds

Configure alerts for the following conditions:

| Alert | Trigger | Required action |
|---|---|---|
| Missing terminal event | Planned/started event has no terminal outcome within SLA | Create reconciliation task; pause destructive processing if material |
| Approval gap | Destructive completion lacks approval reference | Stop execution and investigate |
| Hold bypass attempt | Destructive method called for a held record | Critical incident; stop job and preserve evidence |
| Restricted-class attempt | Ordinary job selects safeguarding/restricted class | Critical configuration or data-classification incident |
| Audit write failure | Event cannot be committed | Fail closed for destructive operations |
| Digest mismatch | Event-chain or payload digest validation fails | Quarantine affected run and investigate tampering/integrity issue |
| Unknown deletion result | Provider outcome cannot be confirmed | Block retry; reconcile manually or through controlled recovery |
| Suppression release spike | Rate exceeds approved baseline | Privacy review and possible rule rollback |
| Unauthorized read/export | Access outside approved role or scope | Security investigation and access review |
| Scheduler overlap | Lock conflicts exceed expected baseline | Check stuck jobs and scheduler behavior |

Alert messages must include batch/run ID, event class, error class, owner, severity, and next action. They must not include personal data or secrets.

## 12. Validation requirements

Before staging deployment, synthetic tests must demonstrate:

1. Every legal state transition creates the expected accepted event and terminal evidence.
2. Illegal transitions create a rejection event and do not mutate the record.
3. Dry-run and review-only modes create planned events but never destructive completion events.
4. Holds, rights requests, incidents, corrections, restricted classes, and failed reconciliation generate block/exception events.
5. Suppression applications, exceptions, removals, and cross-filter blocks are attributable to a rule version and authorized actor.
6. A suppression removal attempt by an unauthorized role is rejected and logged.
7. Duplicate scheduler runs produce one effective transition chain rather than duplicate disposal actions.
8. Retryable failures include bounded retry attempts; permanent failures do not retry.
9. Unknown provider outcomes are reconciled before any retry and never marked completed prematurely.
10. Audit storage failure blocks or pauses destructive processing according to the fail-closed design.
11. Audit events contain no raw names, emails, phone numbers, raw free text, tokens, passwords, or secrets.
12. Derived compliance views contain aggregate counts and no direct identifiers.
13. Tampering with an event digest or previous-event link is detected.
14. Audit access is restricted and itself produces security evidence.
15. Retention review of the audit ledger respects holds and produces a bounded disposal summary.

## 13. Operational acceptance criteria

The specification is ready for staging when the following conditions are met:

| Criterion | Acceptance evidence | Status |
|---|---|:---:|
| Event taxonomy is allowlisted | Versioned event registry | [ ] |
| Schema is deployed in test | Migration or object configuration record | [ ] |
| Audit writer is server-side | Service-account and code review evidence | [ ] |
| Append-only protection works | Update/delete negative tests | [ ] |
| State transitions are complete | Synthetic transition report | [ ] |
| Suppression exceptions are traceable | Exception report and reviewer evidence | [ ] |
| Approvals are enforced | Missing-approval negative test | [ ] |
| Holds and rights gates work | Gate test report | [ ] |
| No sensitive content is logged | Sanitised log and event inspection | [ ] |
| Reports are aggregate-only | View/query review | [ ] |
| Alerting works | Triggered alert evidence | [ ] |
| Recovery works | Timeout, crash, and digest-mismatch tests | [ ] |
| Retention is documented | Approved schedule and disposal runbook | [ ] |
| Privacy/security sign-off complete | Named approvals | [ ] |
