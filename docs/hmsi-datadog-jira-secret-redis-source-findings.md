# Datadog-to-Jira Secret and Redis Source Findings

## Redis

Redis documents using `SET` with the `NX` option to set a key only when it does not already exist, and `EX` or `PX` to assign an expiration. Redis also documents the random-token pattern for lock acquisition and safe release in distributed locking guidance. Sources: https://redis.io/docs/latest/commands/set/ and https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/

For HMSI, idempotency acquisition should use a unique request token with `SET key token NX EX <ttl>`. Release must compare the stored token before deleting, so one worker cannot release another worker’s lock. A durable completed record should be stored separately from a short processing lock.

## Node.js cryptography

Node.js documents `crypto.randomBytes()` as a cryptographically strong random-data generator and notes that it may wait for sufficient entropy. Source: https://nodejs.org/api/crypto.html

For HMSI, HMAC secrets and lock tokens should be generated by an approved secret-management process using cryptographically secure random material. Secret values must not be logged, committed, placed in Jira, or included in Datadog payloads.

## OWASP secret management

OWASP’s Secrets Management Cheat Sheet describes safe rotation as a staged process: create the new secret, set it, test it, and complete the rotation. Source: https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html

For HMSI, HMAC rotation should use an overlap window where the receiver accepts the active and previous secret, while Datadog is switched to the new secret. The old secret should be revoked only after delivery and validation evidence is complete.
