# Volunteer Task-Assignment Model — Implementation Plan

**Status:** Design only. No migration, API mutation, user assignment, notification, or production data change has been performed.

## Design objective

The volunteer portal should support the same safe work loop as the worker and member portals: an authorised administrator creates and assigns a job, an active approved volunteer sees only jobs assigned to that volunteer, the volunteer accepts and progresses the job, and the volunteer submits a private proof link or completion note for review. Volunteers should continue to use the Volunteer Community Room and approved opportunities, but an opportunity application must not automatically become an assignment.

The existing portal uses a signed server-side portal cookie and server-side `getPortalIdentity()` checks. The new model should preserve that boundary rather than exposing the assignment tables directly to browser Supabase clients. Row-level security should remain enabled, with no public table policy; the server API should use the existing service client only after it has independently checked the portal identity and administrator authorization.

## Proposed schema

### `volunteer_assignments`

| Column | Type | Rules and purpose |
|---|---|---|
| `id` | `uuid` | Primary key, generated by `gen_random_uuid()`. |
| `volunteer_id` | `uuid` | Required FK to `volunteer_applications.id`, `ON DELETE RESTRICT`; preserves explicit retention ordering. |
| `source_article_id` | `uuid` | Nullable FK to `news_articles.id`, `ON DELETE SET NULL`; keeps a task if a source dispatch is later archived. |
| `opportunity_id` | `uuid` | Nullable FK to `opportunities.id`, `ON DELETE SET NULL`; allows manual assignment from an approved opening without making the opening the owner of the task. |
| `title` | `text` | Required, length-limited by API validation. |
| `description` | `text` | Required task brief. |
| `required_outcome` | `text` | Required plain-language completion standard. |
| `priority` | `text` | Check constraint: `low`, `medium`, or `high`; default `medium`. |
| `status` | `text` | Check constraint: `assigned`, `accepted`, `in_progress`, `submitted`, `completed`, `rejected`, or `cancelled`; default `assigned`. |
| `due_at` | `timestamptz` | Nullable UTC deadline. |
| `proof_required` | `boolean` | Required, default `false`. |
| `completion_note` | `text` | Nullable; final note submitted by the volunteer or administrator. |
| `assigned_by` | `text` | Required administrator email or actor identifier, not a browser-supplied volunteer value. |
| `accepted_at`, `submitted_at`, `completed_at` | `timestamptz` | Nullable lifecycle timestamps written by the server. |
| `is_deleted` | `boolean` | Required, default `false`; supports the existing retention-safe administrative model. |
| `deleted_at` | `timestamptz` | Nullable recovery/purge metadata. |
| `created_at`, `updated_at` | `timestamptz` | Required UTC audit timestamps. |

Recommended indexes are `(volunteer_id, is_deleted, status, due_at)`, `(source_article_id, is_deleted)`, and `(opportunity_id, is_deleted)`. A partial index on active assignments can keep the portal query small: `WHERE is_deleted = false`. No cascade-hard-delete should be attached from `volunteer_applications` to assignments; assignment retention must be handled explicitly by the approved 30-day cleanup process.

### `volunteer_task_proofs`

Proof links should be separate from the assignment row so a volunteer can submit a revised link without overwriting the audit history.

| Column | Type | Rules and purpose |
|---|---|---|
| `id` | `uuid` | Primary key. |
| `assignment_id` | `uuid` | Required FK to `volunteer_assignments.id`, `ON DELETE CASCADE`; a proof has no meaning without its task. |
| `submitted_by` | `uuid` | Required FK to `volunteer_applications.id`, `ON DELETE RESTRICT`; preserves who submitted the evidence. |
| `drive_url` | `text` | Required HTTPS Google Drive/Docs URL validated with the existing `parsePersonalGoogleDriveUrl()` helper. |
| `note` | `text` | Optional length-limited context. |
| `status` | `text` | Check constraint: `pending_review`, `accepted`, `needs_revision`, or `link_cleared`. |
| `reviewed_by` | `text` | Nullable administrator actor. |
| `reviewed_at` | `timestamptz` | Nullable UTC review timestamp. |
| `created_at` | `timestamptz` | Required UTC submission timestamp. |

The API should instruct the volunteer to share the file as Viewer with the named HMSI administrative account and retain the original until ingestion is confirmed. A proof URL must never be made public, logged in raw form, or returned to another volunteer.

### `volunteer_task_events`

Create an append-only audit table with `id`, `assignment_id`, `actor_auth_user_id`, `actor_email`, `actor_role`, `action`, `from_status`, `to_status`, `detail`, and `created_at`. The detail field should contain safe operational context, not passwords, cookies, access tokens, or raw setup links. Events should be inserted by the server after each accepted state transition and administrator action.

## Lifecycle and authorization

The only valid volunteer state transitions should be enforced in server code and repeated in database checks where practical:

| Current state | Allowed actor | Next state |
|---|---|---|
| `assigned` | The assigned active volunteer | `accepted` or `in_progress` if the product keeps one-click acceptance. |
| `accepted` | The assigned volunteer | `in_progress`. |
| `in_progress` | The assigned volunteer | `submitted` when the required note/proof has been supplied. |
| `submitted` | Administrator | `completed`, `needs_revision`, or `rejected`. |
| Any open state | Administrator | `cancelled` or reassigned through a new assignment record. |
| `completed`, `rejected`, `cancelled` | Nobody except an explicitly authorised administrator recovery action | No ordinary volunteer transition. |

A volunteer request must obtain `getPortalIdentity(request)`, require `identity.role === 'volunteer'`, require the corresponding `volunteer_applications.id` to be the assignment’s `volunteer_id`, and re-check `status = 'approved'`, `account_status = 'active'`, and `is_deleted = false`. The administrator endpoints must continue to require the existing administrator session and same-origin protections. Never trust `volunteer_id`, `assigned_by`, `actor_email`, or role values from the browser request body.

## API changes

### Unified portal task feed

Extend `GET /api/portal/tasks` with a volunteer branch that selects only the assigned volunteer’s non-deleted rows and returns `required_outcome`, `proof_required`, and the latest safe proof status. The existing worker and member branches should remain unchanged. The response should include a role-specific message only when there are no volunteer jobs; it should not imply that a volunteer account is unapproved.

Extend `PATCH /api/portal/tasks` with a volunteer branch. Accept only the assignment ID, requested status, completion note, and—if the product chooses inline submission—the proof record ID created by the protected proof endpoint. Apply a conditional update such as `WHERE id = supplied_id AND volunteer_id = identity.profileId AND status = expected_current_status AND is_deleted = false`; this prevents stale tabs and cross-volunteer updates. Insert a corresponding event after the update.

### Proof submission

Add `POST /api/portal/tasks/[id]/proofs` or `POST /api/portal/volunteer-tasks/[id]/proofs`. It must verify the portal identity, verify ownership of the assignment, validate the Google Drive/Docs URL, enforce a maximum note length, insert `volunteer_task_proofs`, and write a `proof_submitted` event. Add a protected `GET` for the volunteer’s own proofs and an administrator-only review endpoint for accepting or requesting revision. Do not use a public upload endpoint for these links.

### Administrator assignment controls

Add `GET/POST /api/admin/volunteer-assignments` for administrator-only listing and creation, and `PATCH /api/admin/volunteer-assignments/[id]` for controlled reassignment, cancellation, completion review, and proof review. Creation must verify the target volunteer is approved, active, and fully onboarded; validate title, description, required outcome, priority, due date, and optional source article/opportunity; then insert the assignment and audit event. Notification dispatch should use the existing official onboarding sender and should record only delivery status and message ID, not message secrets or raw proof links.

A reassignment should close or cancel the old assignment and create a new auditable assignment, rather than silently changing ownership. Bulk actions should use the same per-row authorization and status checks and return affected/skipped counts without leaking volunteer records to unauthorised callers.

## Portal integration

The volunteer workspace should add a `My jobs` section beside `Volunteer Community Room`, `Opportunities`, `Submit proof`, and sign-out. Each job card should show the title, brief, required outcome, priority, due date, source attribution if present, current status, and a clear action button. A `View full job` expansion should show the complete instructions. A `Submit proof link` action should open the protected proof form with the assignment context and explain that the original Drive file must remain available until HMSI confirms ingestion.

The opportunities section should continue to list only open opportunities whose audience is `volunteer` or `both`. Applying for an opportunity creates an application for administrator review; it must not silently create a volunteer assignment. Room access remains enforced by the existing matching-role room API.

## Migration sequence

1. Add the SQL migration to the repository and review it for dependency order, check constraints, indexes, RLS enablement, and non-destructive defaults.
2. Apply the migration once through the approved Supabase migration path. Do not use ad hoc DML or seed real volunteer assignments.
3. Verify table names, columns, constraints, indexes, RLS state, and policies through bounded `information_schema` and PostgreSQL catalog queries. Do not select volunteer rows.
4. Deploy API reads behind a feature flag or an empty-result-safe branch. The existing volunteer workspace should continue to render opportunities and room access if the new table is empty.
5. Deploy administrator creation and proof review after the read path is verified. Create no production assignment during this rollout unless separately authorised.
6. Enable volunteer task display and notification dispatch only after a disposable test identity has completed the controlled integration test.

The migration should not alter existing worker/member tasks, Auth records, password setup links, or retention tables. It should also avoid a database-level trigger that sends email; notifications should remain in the server route where authorization, idempotency, and safe delivery logging are visible.

## Test plan

| Test area | Required cases |
|---|---|
| Authorization | Unauthenticated requests return 401; a worker/member cannot read or mutate volunteer assignments; a volunteer cannot read another volunteer’s job; non-admins cannot create or reassign jobs. |
| Eligibility | Pending, rejected, inactive, or removed volunteers cannot receive or act on a job. An opportunity application alone cannot create one. |
| Lifecycle | Valid transitions succeed; repeated clicks are idempotent or safely rejected; stale status updates do not overwrite newer work; closed jobs cannot be changed by volunteers. |
| Proof | Invalid host, non-HTTPS URL, oversized note, wrong assignment, and another volunteer’s assignment are rejected. Valid private Drive links are stored and returned only to the owner or authorised administrator. |
| Audit | Assignment, acceptance, progress, proof submission, revision request, completion, cancellation, and reassignment create safe events without raw secrets or tokens. |
| Retention | Soft deletion hides a job from active portal feeds; recovery metadata is retained; final purge ordering respects restrictive foreign keys and the approved 30-day policy. |
| UI | Each role sees only its own menu, room, jobs, opportunities, and proof links; mobile controls remain keyboard accessible; loading, empty, error, and success states are explicit. |

## Operational safeguards

Use an idempotency key for administrator assignment creation so a double click does not create duplicate jobs or duplicate notification emails. Keep API responses bounded and avoid returning volunteer directory data to the volunteer portal. Rate-limit proof submissions and state changes. Use UTC timestamps in storage and localised display only in the client. Add monitoring for repeated 403/409/503 responses, but never log passwords, portal cookies, Supabase tokens, raw Drive links, or email credentials.

The safest first release is therefore a new volunteer assignment table, a separate proof table, protected server routes, and a feature-flagged portal branch. It does not require changing authentication, creating an immediate cascade delete, or converting every opportunity application into a job.
